## 修复内容

| 缺陷 | 修复及验证意义 |
| --- | --- |
| 相同 CLR 类型在不同导航下重复 Owned、嵌套 Owned 解析错误 | 从实际导航目标解析 EF metadata，支持不同列名及 converter；覆盖多层、重复类型和仅 Owned 属性的更新选择。 |
| Owned / 表拆分 / 继承 / query filter 对复杂 RETURNING SQL 的组合失败 | 复杂输出先进入结果表，再由 EF 组合普通查询；简单实体保留直接输出路径。生成主键、默认值、筛选实体输出和清理均有回归。 |
| 复合键按字符串拼接产生碰撞，null 与字面字符串混淆 | 使用结构化键比较与 hash；覆盖下划线歧义、null / "null" 以及数组键。 |
| 回填数据库 null 后原属性仍保留旧值 | 允许向引用/可空属性写入 null，保留非可空值类型保护；BulkRead 的值和集合替换均验证。 |
| `char(n)` / `character(n)` COPY 被映射到驱动内部字节 char | 改为 `bpchar`，包括数组及带类型修饰的映射；实际 Flight char、枚举 converter 通过。 |
| 外部事务中的 BulkSaveChanges flush 后 tracker 未接受，UoW 再次保存 | 成功 flush 后接受已处理状态；修复自有事务异步创建、提交、释放及连接开闭引用平衡，不提交或释放调用方事务。 |
| 默认 BulkSaveChanges 绕过 Monica / FIPS 保存策略 | 新增显式 `PreserveSaveChangesPipeline`，调用多态普通 EF SaveChanges；审计、同步、软删除、stamp/version、Outbox、任意并发 token 保留。 |
| 直接二进制 COPY 绕过 EF 命令生命周期守卫 | 直接 COPY 前执行可拦截的 `SELECT 1`；已结束/失败 UoW 在同步、异步路径均拒绝写入。临时表路径已有可拦截命令。 |
| 批次内重复解析类型、converter 和属性路径 | 按批次预计算并缓存列元数据和访问路径；大批量真实写入回读验证。 |
| 普通 build/test 自动打包牵连其他 provider 的稳定版依赖预览版错误 | 默认不随 build 自动 pack；显式 `dotnet pack` 保留并已验证。 |

命令预检只负责触发 EF 命令守卫，不执行 SaveChanges 策略，也不能使任意命令重写 interceptor 自动应用于二进制 COPY。

### 复杂实体覆盖

- 真实 Flight：20 个根标量；Plan / AircraftInfo / RouteInfo 三个同表 Owned 共 37 个 metadata 属性（包含所有权键）；DepInfo / ArrInfo / RteInfo 子实体；复合键 FlightLabels。逐集合 Bulk 增读改删、选择性 Owned 更新、输出回填、共享主外键、枚举转换和 interval 后由普通 EF 重新查询核对。
- 真实 User.UserInfo 深层 JSON、日期和清空为 null；FileTemplate.Content 集合的写入、更新与读回。
- 真实 MAPlan：生产加密扩展和 converter；检查物理列为密文、普通 EF 解密、加密查询参数、BulkRead 和更新。
- 真实 MessageCircuitState：生产 Revision 并发 token，保留保存管线后拒绝旧快照。
- 合成 Flight：三个 Owned、生成 ID、共享主键子实体、标签和嵌套备注；合成 Airway：共享航点、航段、自然键和删除引用保护。
- 合成 DeepMission：约 40 个根字段，decimal、日期、Guid、枚举式字符串、数组、JSON；根→航段→航路点→限制四层，加机组集合，共五张表。普通 EF 与逐实体集 Bulk 均验证，最后核对所有表计数恢复。
- 事务、取消和生命周期：普通 EF 与 Bulk 共事务回滚、早期 flush 后业务与 Outbox 一起回滚、取消清理、调用方事务所有权、UoW 成功或失败后拒绝后续写入。

逐实体集的 Bulk 不会隐式遍历整个业务图。父子写入顺序、外键传播、共享引用以及删除顺序由调用方在一个事务中明确组织。

## 已存在问题与接入条件

### 1. 默认 A 兼容模式不能直接承诺原生 DateOnly 全部工作

当前服务器默认新库兼容模式为 A，SQL `date` 实际返回 `timestamp without time zone`。全模型在 A 库中为 7 通过、2 失败：MAPlan DateOnly 的二进制 COPY 报 `08P01: insufficient data left in message`；MessageCircuitState 的 DateOnly 读取报 `InvalidCastException`。

[原生驱动独立探测](package-smoke/native-a-probe.json)完全不调用 Bulk API，仍复现同样两类错误；普通参数化 DateOnly 写入可成功，但读回类型不匹配。本轮真实模型 9/9 使用显式 `DBCOMPATIBILITY = 'PG'` 的独立新库。

已有应用需要先确认实际 schema 和驱动日期映射，选择兼容的数据库日期类型或明确的应用转换。库安装过程不会改变已有数据库模式，也没有加入仅使 Bulk 成功、却仍令普通 EF 读取失败的隐式规避。

### 2. FIPS 原有共享测试的三项失败

原始官方依赖和 fork 替换依赖两轮失败名称完全相同：

1. `FipsObjectMappingCompositionTests.ObjectMappingProfiles_ShouldOwnUniqueMappingPairs`：多个对象映射 profile 注册重复映射对。
2. `ShardingCompatibilityTests.IsolatedProviderTransaction_ShouldCommitOrRollbackBothTables`，GaussDB / commit=true。
3. 同一分片测试，GaussDB / commit=false。

后两项在普通 EF SaveChanges 写入审计时间时即失败：UTC DateTime 写入 `timestamp without time zone` 被驱动拒绝，未调用 Bulk。rollback 用例因此在预期的业务回滚异常之前失败。三个 PostgreSQL 用例因未配置 PostgreSQL 测试连接而跳过。

共享套件中实际 GaussDB 分片迁移 SQL、SQLite 分片及其他已通过项保持通过。本轮结果支持已覆盖范围没有新增失败，不能将失败的 GaussDB 分片事务用例描述为已经通过。问题属于当前应用映射/驱动契约，未在通用 Bulk 库中替 FIPS 改写生产行为。

### 3. 业务保存语义必须明确选择

需要 Monica/FIPS 的正常业务保存时，继续使用正常仓储/UoW 保存，或使用：

```csharp
await context.BulkSaveChangesAsync(new BulkConfig
{
    PreserveSaveChangesPipeline = true
});
```

该选项执行派生 DbContext 的普通 SaveChanges，保留审计、软删除、同步属性、ConcurrencyStamp、EntityVersion、Revision、Outbox 和拦截器。它提供语义兼容，不提供 COPY 速度。

直接 `BulkInsert` / `BulkUpdate` / `BulkDelete` 及默认 BulkSaveChanges 是技术批量路径。调用方负责业务字段与副作用；BulkDelete 默认物理删除，任意并发 token 不会自动变成逐行乐观并发检查，业务事件和 Outbox 不会自动投影。不能把所有正常业务保存统一替换成默认 BulkSaveChanges。

### 4. 分片与完整图不是隐式路由能力

Raw Bulk 不能自动把 ShardingCore/FIPS 的逻辑实体按月份路由至物理上下文。需要使用应用既有分片路由取得正确物理上下文和表名，按目标分组，并加入已有事务。当前通用 Bulk 的通过结果不代表动态分片的全业务路径已经验证。

复杂图应按实体集合在显式事务内处理：父表→输出主键→赋子表外键→子表；删除遵循外键顺序。GaussDB 不支持的操作仍显式抛错，具体见 [provider 文档](../EFCore.BulkExtensions.GaussDB/README.md)。
